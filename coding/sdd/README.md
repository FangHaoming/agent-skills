# SDD riper Skill 使用指南

## 1. 目标

沉淀一份团队可复用的 `skill` 使用说明，统一大模型协作时的输入方式、阶段门禁和文档回写习惯，避免直接裸改代码、上下文漂移和方案失控。

## 2. 核心原则

1. `No Spec, No Code`
2. `No Approval, No Execute`
3. `Spec is Truth`
4. `Reverse Sync`
5. 所有发现优先回写 `Spec`，不要只留在对话里

一句话理解：

- `RIPER` 管流程
- `Spec` 管记录
- 模型按需取用上下文，不依赖长对话记忆

## 3. Skill 选型

### `sdd-riper-one`

适用于：

- 中大型需求
- 陌生模块或老项目接手
- 跨模块、跨项目改动
- 需要方案对比、阶段门禁、多人协作
- 需要沉淀长期资产，如 `Spec`、`CodeMap`、`ProjectMap`

### `sdd-riper-one-light`

适用于：

- 小需求
- 小范围 bugfix
- 文案、样式、局部逻辑调整
- 边界清晰、改动面小
- 已经熟悉模块，希望低心智成本推进

### 可不使用 skill 的情况

仅限纯机械性、小到几乎无决策的修改，例如：

- typo 修复
- 注释补充
- 配置值微调

一旦发现复杂度上升，立即切回 `sdd-riper-one-light` 或 `sdd-riper-one`。

## 4. 最佳实践

1. 新团队默认先用 `sdd-riper-one`，先建立流程纪律，再逐步切轻量模式。
2. 先让 AI 产出 `Spec` 或 `micro-spec`，不要上来就要求写代码。
3. `Plan Approved` 是讨论和执行的分水岭，未批准前只做分析和收敛。
4. 大任务先缩小范围，按 `CodeMap -> Spec -> Plan -> Execute -> Review` 推进。
5. 不要让 AI 全仓盲扫，优先让它进入与本次任务直接相关的局部。
6. 执行后把 `Change Log`、验证结论、偏差和后续动作回写文档。
7. `Review` 只校验“文档说的和代码做的是否一致”，不要顺手扩需求。

## 5. 标准使用步骤

### 场景 A：中大型需求

1. 启用 `sdd-riper-one`
2. 准备输入材料
   - 需求文档
   - 设计稿
   - 讨论记录
   - 约束文档
3. 补齐前置资产
   - `CodeMap`
   - `Context Bundle`
   - 首版 `Spec`
4. 先让 AI 做事实梳理和方案收敛
5. 要求输出原子级 `Plan`
   - 文件路径
   - 函数签名
   - 执行顺序
   - 验证方式
6. 人工批准 `Plan`
7. 再进入代码实现
8. 实现后做 `Spec vs Code Review`
9. 回写 `Spec`

### 场景 B：小需求 / 小修复

1. 启用 `sdd-riper-one-light`
2. 先输出 `micro-spec`
3. 列出最小改动文件和风险点
4. 等确认后执行
5. 输出 `Change Log`
6. 如果影响行为、接口、约束或流程，同步更新 `Spec`

## 6. 适用场景清单

### 适合重流程 skill

- 需求变更较多，容易反复
- 逻辑链路长，单靠聊天容易丢信息
- 涉及兼容、权限、缓存、状态、接口联动
- 需要交接、复盘、复用

### 适合轻量 skill

- 小范围前端交互调整
- 空指针、边界判断、提示文案修复
- 局部样式改动
- 单页面内的有限逻辑修改

### 不建议直接轻量执行

- 改动跨多个入口
- 需求尚未定稿
- 存在历史兼容风险
- 需要重构、迁移或公共接口调整

## 7. 需求变更时怎么做

需求变更时的原则是：**先更新文档，再实现代码；先通过 Plan，再进入 Execute。**

### 7.1 先判断变更影响范围

至少检查这些方面：

- 页面入口、调用链和复用方
- 相关组件、store、context、service、utils
- 请求参数、响应字段、默认值、容错逻辑
- `loading / empty / error / success` 四类状态
- 权限、灰度、环境判断、多语言文案
- URL、缓存、刷新、返回、恢复场景
- 埋点、日志、下载、分享等旁路能力
- 旧数据、旧交互、历史兼容

### 7.2 先更新 `Spec`

需求变更后，不要直接沿用旧计划改代码，先更新文档中的这些部分：

1. `目标`
2. `范围`
3. `约束`
4. `风险`
5. `Checklist`

如果是替换旧实现，还要补充：

- 哪些行为保持不变
- 哪些行为发生变化
- 是否需要兼容旧数据或旧参数

### 7.3 基于新 `Spec` 重新出 `Plan`

要求 AI 给出新的实施计划，至少包括：

- 受影响文件
- 关键函数或模块
- 执行顺序
- 每一步的验证方式
- 兼容与回滚关注点

### 7.4 `Plan Approved` 后再改代码

此时才能进入实现。执行时建议遵循：

1. 先做最小可用改动
2. 再补齐异常态、兼容逻辑和边界处理
3. 最后补验证、测试、文档同步

### 7.5 执行后回写文档

如果实际代码落地与原计划有偏差，需要按 `Reverse Sync` 回写：

- 实际改动了什么
- 哪些判断在执行中被修正
- 哪些风险已关闭，哪些仍保留
- 当前是否达到 `Done Contract`

## 8. 推荐提示词

### 8.1 复杂需求

```text
请启用 $sdd-riper-one。
这是一个需要文档先行的任务，请先不要改代码。
需求：[描述/需求文档路径/后端接口文档/设计稿路径]

先帮我完成以下事项：
1. 基于现有需求和代码现状，梳理影响范围
2. 输出或更新本次任务的 Spec，至少包含：目标、范围、约束、风险、Checklist
3. 基于更新后的 Spec，给出原子级 Plan，精确到文件路径、关键函数、执行顺序、验证方式

等我确认 Plan 后，再进入 Execute。
```

### 8.2 小需求 / 小修复

```text
请启用 $sdd-riper-one-light。
这是一个小任务，请先不要直接改代码。
需求：[描述/需求文档路径/后端接口文档/设计稿路径]

先输出：
1. micro-spec
2. 最小改动计划
3. 受影响文件
4. 风险和验证方式

等我确认后再执行。
```

### 8.3 需求变更

```text
请启用 $sdd-riper-one。
这次是需求变更，不要直接沿用旧方案改代码。
需求：[描述/需求文档路径/后端接口文档/设计稿路径]
Spec ：[引用需求相关 Spec ]

请先：
1. 对照现有 Spec 标出变更点
2. 更新 Spec 中的目标、范围、约束、风险、Checklist
3. 明确哪些行为不变，哪些行为改变，是否需要兼容旧数据或旧参数
4. 基于更新后的 Spec 重新输出 Plan

等我批准 Plan 后，再开始代码修改。
```

## 9. 最小 Spec 模板

```md
# <任务名>

## 目标

- 要解决什么问题
- 这次交付的用户价值是什么

## 范围

- 涉及哪些页面、模块、路由或服务
- 明确不在本次范围内的内容

## 约束

- 兼容要求
- 性能要求
- 权限、灰度、环境限制

## 风险

- 可能影响的旧逻辑
- 当前未知项

## Checklist

- [ ] 影响范围已确认
- [ ] Plan 已批准
- [ ] 核心链路已实现
- [ ] 异常态和兼容逻辑已补齐
- [ ] 验证完成
- [ ] Spec 已回写
```

## 10. 团队约定建议

建议至少固定以下约定：

1. 未经 `Plan Approved` 不得改代码
2. 文档可以先改，代码后改
3. 变更影响需求、行为、接口、约束、流程或实现决策时，必须更新 `Spec`
4. 连续多轮只在搜索和阅读时，应停止发散，收敛到最小改动面
5. 默认先完成核心链路，再补周边，不顺手扩范围

## 11. 一句话结论

`skill` 的最佳实践不是“写更长的 prompt”，而是把任务先收敛成文档，再让 AI 按批准过的计划执行，并把结果重新沉淀回文档。
