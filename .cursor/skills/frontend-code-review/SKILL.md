# Frontend Code Review

## 适用场景

当用户要求以下任一任务时使用本 skill：

- review PR / MR / diff
- review 前端改动、页面改动、组件改动
- 审查 React / Vue / Next.js / Vite / TypeScript / CSS 相关变更
- 检查可访问性、性能、语义化 DOM、可维护性或测试覆盖

如果本次 review 明显是后端、基础设施或数据任务，不要硬套本 skill。

## 目标

输出高信号的前端审查意见，而不是罗列低价值样式建议。

每条反馈至少满足以下之一：

- 能阻止真实 bug、回归、线上事故或安全问题
- 能指出明显的可访问性、语义或交互缺陷
- 能减少后续维护成本、排查成本或测试盲区
- 能提示必须人工验证的视觉或交互风险

## 审查原则

1. 先看正确性，再看风险，再看体验，再看整洁度。
2. findings 必须优先于总结，按严重级别排序。
3. 只报有证据的问题；不要基于猜测下结论。
4. 已由格式化、lint、类型系统稳定兜底的纯风格噪音，默认不报。
5. 如果风险依赖运行态、真实接口、设计稿或浏览器行为才能确认，标记为“需人工验证”，不要伪装成已确认 bug。
6. 优先结合项目已有约定、组件模式、设计 token、状态管理方式来判断，不要脱离上下文套通用规范。

## 审查流程

### 1. 先收集上下文

- 只关注本次变更涉及的文件和直接影响的调用链
- 识别技术栈：React / Vue / Next.js / CSS Modules / Tailwind / Zustand / Redux / 表单库 / 路由方案
- 看是否存在 lint、测试、类型检查、构建脚本等已有安全网

### 2. 逐层筛查

按以下顺序检查：

1. 正确性与状态流
2. 可访问性与语义结构
3. 安全与数据边界
4. 性能与渲染稳定性
5. 样式健壮性与响应式
6. 可维护性与复用边界
7. 测试覆盖与回归风险

详细检查点见 [CHECKLIST.md](CHECKLIST.md)。

### 3. 组织输出

默认使用以下严重级别：

- `[阻塞]`：高概率导致 bug、崩溃、数据错误、安全问题、严重无障碍缺陷
- `[重要]`：明显的行为风险、可维护性风险、性能风险、较大的可访问性问题
- `[建议]`：值得改进但不一定阻塞合并
- `[需人工验证]`：从 diff 能看到风险，但需要运行、联调、视觉验收或多端验证
- `[轻微]`：合并后统一处理也可以的小问题；尽量合并表达，不要刷屏

## 前端专项要求

### 语义与可访问性

- 检查交互元素语义是否正确：`button`、`a`、`label`、表单控件、列表、表格
- 检查标题层级、键盘可达性、焦点可见性、替代文本、aria 使用是否合理
- 如果 DOM 结构明显不语义化，直接指出结构性问题，而不是只提 class 或样式

### 正确性

- 关注空态、loading、error、边界输入、竞态、受控/非受控切换、依赖项遗漏
- 检查异步状态是否可能造成脏更新、重复请求、闪烁或状态回滚
- 检查列表 key、条件渲染、表单提交、事件绑定与清理

### JS / TS 类型与语言特性

- 检查类型系统与运行时边界是否一致，尤其是接口返回、URL 参数、本地存储、表单值等外部输入
- 重点关注 `enum` / union / 常量对象分支是否完整，新增成员后是否可能漏处理
- 对离散字符串或数字常量，检查是否避免了散落硬编码；TS 倾向集中建模，JS 倾向使用 `Object.freeze` 常量对象统一引用
- 检查 `any`、类型断言、非空断言、`@ts-ignore` 是否掩盖真实风险
- 对“类型看起来安全，但运行时可能出错”的代码优先报问题

### 性能

- 检查不必要重渲染、昂贵计算、超大依赖传播、无意义 memo、render 中创建重对象
- 检查图片、资源、懒加载、代码分割、动画和滚动相关风险
- 不要为了“可能更快”而给出缺少证据的微优化建议

### 安全

- 重点看 `dangerouslySetInnerHTML`、URL 拼接、富文本、文件上传、跳转、鉴权控制、敏感信息暴露
- 对输入、输出、权限判断、错误信息暴露保持敏感

### 可维护性

- 检查组件职责是否过载、重复结构是否该抽离、命名是否表达业务语义
- 检查样式耦合、魔法值、硬编码 token、跨层依赖、难测结构

## 输出格式

如果发现问题，按以下结构输出：

1. 先列 findings，按严重级别从高到低排序
2. 每条包含：
   - 严重级别
   - 结论
   - 为什么是问题 / 可能后果
   - 简短修复方向
   - 必要时标注“需人工验证”的前提
3. 然后再补：
   - open questions / assumptions
   - 简短 change summary

## 表达要求

- 直接、明确、面向工程落地，不写空泛表扬
- 尽量指出“影响”而不是只说“这里不太好”
- 不要把多个独立问题混在一条里
- 不要为了凑数量而输出低价值意见
- 如果没有发现明确问题，要清楚说明“未发现明显问题”，并补充残余测试风险或人工验证点

## 自检

输出前确认：

1. 是否所有 findings 都基于当前改动和上下文
2. 是否把真正的 bug / 回归风险排在最前
3. 是否避免了纯代码风格噪音
4. 是否覆盖了前端高风险区域：语义、交互、状态、JS/TS 类型边界、性能、安全、测试
5. 是否把无法从静态 diff 确认的问题降级为“需人工验证”
