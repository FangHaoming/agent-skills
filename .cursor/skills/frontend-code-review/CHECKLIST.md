# Frontend Review Checklist

按需使用，不要机械逐项复读。优先检查与本次变更直接相关的条目。

## 1. 正确性与状态

- 事件处理是否绑定到正确节点，是否会误触发或漏触发
- `useEffect` / watcher / subscription 是否有遗漏依赖或缺少清理
- 异步请求是否存在竞态、重复提交、过时响应覆盖新状态
- 列表 `key` 是否稳定，条件渲染切换是否会导致状态错位
- 表单是否有默认值、校验、提交态、防重复提交与失败兜底
- 空态、loading、error、无权限态是否完整

## 2. JS / TS 语言与类型边界

- 是否把 TypeScript 类型当作运行时保证，遗漏了接口返回、URL 参数、`localStorage`、表单值等外部数据校验
- 是否滥用 `any`、双重断言、非空断言 `!`、`as`，掩盖真实空值或类型分支问题
- 联合类型是否完成收窄；分支逻辑是否依赖脆弱字符串判断而不是明确判别字段
- `enum`、字符串字面量联合、常量映射是否使用一致；是否出现值变更后调用方静默失配的问题
- 对离散的字符串/数字业务值，是否仍在多个位置硬编码；TS 中是否应抽成 `enum` 或字面量联合，JS 中是否应抽成 `Object.freeze` 常量对象后统一引用
- `switch` / 条件分支是否覆盖完整，新增枚举值或 union 成员后是否会漏处理
- 比较逻辑、展示文案、样式分支、接口参数是否复用了同一组常量来源，而不是手写多个近似字面量
- 可选链、空值合并、默认值是否掩盖非法输入，导致错误静默吞掉或 UI 显示伪正常数据
- 泛型、工具类型、类型别名是否真的提升约束，而不是把业务模型包得更难理解
- 是否引入 `@ts-ignore` / `@ts-expect-error` / 宽泛类型兜底却没有说明原因与收敛计划
- class、原型、`this` 绑定、装饰器等 JS 特性是否引入上下文丢失或编译产物兼容性风险

## 3. 语义化 DOM 与可访问性

- 可点击元素是否使用原生 `button` / `a`，避免 `div` / `span` 模拟交互
- 列表是否使用 `ul` / `ol` / `li`，表格是否使用 `table` 语义
- 表单控件是否有正确关联的 `label`
- 模态框、抽屉、菜单、Popover 是否有焦点管理与键盘退出路径
- 图标按钮、图片、SVG 是否有可访问名称或替代文本
- 标题层级、ARIA 属性、禁用态与提示信息是否合理

## 4. 性能与渲染稳定性

- 是否把昂贵计算、对象字面量、函数创建放在热路径 render 中
- 是否存在无意义的大范围状态订阅或 props 级联
- 是否误用 `memo` / `useMemo` / `useCallback`，导致复杂度上升却无收益
- 图片、长列表、懒加载、动画、滚动监听是否可能造成卡顿
- 是否有首屏体积明显膨胀、重复请求或不必要同步阻塞

## 5. 安全与边界

- 是否直接注入 HTML、拼接脚本、拼接跳转 URL 或信任未清洗内容
- 用户输入、查询参数、富文本、上传文件是否经过校验与限制
- 是否暴露 token、内部接口、调试信息、PII 或多余错误细节
- 前端权限控制是否只是“隐藏按钮”，但未处理真实调用风险

## 6. 样式与体验健壮性

- 是否依赖脆弱布局，例如固定高度、绝对定位堆叠、魔法值间距
- 文本过长、缩放、换行、本地化后是否容易溢出或错位
- 深色模式、禁用态、hover/focus/active 态是否一致
- 响应式断点、滚动容器、sticky、覆盖层层级是否可靠
- 是否错误覆盖设计 token，或把主题值硬编码进组件

## 7. 可维护性

- 组件是否职责过多，是否应拆分子组件或 hook
- 业务语义是否清晰，命名是否能表达职责
- 是否引入重复逻辑、重复样式、重复常量
- 是否把临时兼容逻辑硬编码为长期结构
- 是否让测试、复用、后续替换变得更困难

## 8. 测试与验证

- 新逻辑是否缺少必要单测 / 组件测试 / 集成测试
- 现有测试是否真的覆盖这次改动的关键路径，而不是仅覆盖实现细节
- 如果是视觉改动，是否至少指出需要做的人工验证场景
- 如果是交互链路改动，是否指出关键回归点

## 严重级别建议

- `阻塞`：明确 bug、安全问题、数据错误、严重 a11y 问题
- `重要`：高概率回归、明显性能风险、结构性问题
- `建议`：可维护性或体验改进
- `需人工验证`：静态 diff 无法确认，但风险值得提醒
- `轻微`：合并表达的小问题，避免刷屏
