# Frontend Semantic DOM

## 适用场景

当你要生成或重构前端结构时使用本 skill，包括但不限于：

- 页面骨架
- React / Vue / HTML 模板
- 列表、卡片、导航、表单、表格、弹窗、侧栏
- 根据设计稿还原前端结构
- 用户明确指出 DOM 混乱、嵌套过深、语义差、维护困难

目标不是只让页面“看起来对”，而是让结构本身也清晰、可靠、易维护。

## 核心原则

1. 先设计内容语义，再设计布局容器，再补样式挂载点。
2. DOM 首先服务于信息层次、交互职责和可维护性，而不是机械还原视觉稿分组。
3. 优先使用语义化标签，非必要不使用 `div` / `span`。
4. 控制层级深度，减少无意义包裹。
5. 重复结构优先抽成子组件，而不是复制粘贴大段相似模板。
6. 交互元素必须语义正确，避免“看起来像按钮”的非按钮实现。

## 生成流程

### 第一步：识别内容类型

在写代码前，先判断当前区域属于哪一类内容：

- 页面级区域：`header`、`main`、`aside`、`footer`、`nav`
- 独立内容块：`section`、`article`
- 列表型内容：`ul` / `ol` / `li`
- 表单型内容：`form`、`fieldset`、`legend`、`label`
- 数据表格：`table`、`thead`、`tbody`、`tr`、`th`、`td`
- 操作区：工具栏、筛选栏、按钮组
- 弹层区：对话框、抽屉、菜单、提示层

如果一个区域能被明确归类，就优先采用对应语义结构，而不是退回通用 `div`。

### 第二步：先搭语义骨架

输出结构时，先确定以下问题：

- 页面主内容是不是应该放进 `main`
- 一个独立模块是不是应该用 `section` 或 `article`
- 一组导航入口是不是应该用 `nav`
- 一组重复卡片是不是应该用 `ul > li`
- 一组表单控件是不是应该使用 `form` 和 `label`
- 一组二维数据是不是应该用 `table`

先完成语义骨架，再添加必要的布局容器和 className。

### 第三步：压缩无意义层级

每新增一层节点前，都检查：

- 这层是否提供了明确语义
- 这层是否承担布局、定位、裁剪、滚动、状态切换等真实职责
- 去掉这层后是否仍可实现同样效果

如果答案是否定的，就不要增加该包裹层。

### 第四步：保证交互语义正确

- 页面跳转、外链、路由入口用 `a`
- 表单提交、普通操作、开关触发用 `button`
- 表单项必须有关联 `label`
- 单选/复选/输入控件要保持原生语义，不要用 `div` 模拟
- 可展开分组、说明性标题、区域标题要体现正确标题与层级关系

不要用以下错误替代：

- `div` 冒充按钮
- `span` 冒充链接
- 裸文本直接充当表单标签
- 纯样式容器承担真实交互语义

## 标签优先级

当多个实现都能完成视觉效果时，优先选择语义更强的标签：

- 页面主体优先 `main`，不是 `div.main`
- 导航优先 `nav`，不是 `div.menu`
- 独立条目优先 `article` 或 `li`，不是 `div.item`
- 列表优先 `ul/ol`，不是一组并列 `div`
- 表单优先 `form` / `label`，不是 `div + input + div`
- 数据展示优先 `table`，不是“看起来像表格”的多列 `div`
- 重要标题优先 `h1-h6`，不是只有样式放大的 `div` / `span`

## DOM 设计规则

### 列表

- 重复性的同类信息使用 `ul` / `ol` / `li`
- 卡片列表、菜单列表、消息列表、标签列表、操作列表都优先按列表处理
- 不要把一组同构条目写成多层 `div > div > div`

### 表单

- 用户提交或筛选区域优先使用 `form`
- 每个输入控件都应该有可关联的 `label`
- 同一语义组的选项优先考虑 `fieldset` + `legend`
- 错误提示、帮助文本、必填状态应围绕表单语义组织

### 表格

- 行列关系明确的数据使用 `table`
- 表头使用 `th`
- 不要为了方便写样式，把真正的表格数据重构成普通 `div`

### 卡片与内容块

- 独立可复用的内容单元优先用 `article`
- 页面中的主题分区优先用 `section`
- 仅承担布局的一层容器才使用 `div`

### 标题结构

- 保持合理的标题层级
- 不要为了字体大小而滥用标题标签
- 也不要在应当是标题的地方只写普通 `div`

## 组件拆分规则

满足以下任一情况时，优先考虑拆分子组件：

- 同类 DOM 结构重复出现 2 次及以上
- 单个组件模板过长，阅读时无法快速识别区域职责
- 一个局部区域已经具备独立职责，如筛选栏、卡片、表单项组、分页器、侧边信息块
- 不同区域的状态、事件、样式职责已经明显分离

拆分目标是让模板结构反映业务结构，而不是把所有内容堆在一个文件里。

## 命名规则

- `className` / 类名优先表达业务语义或组件职责
- 避免低信息量命名，如 `box`、`box1`、`wrap`、`inner`、`left`、`right`、`content1`
- 能命名成 `user-card`、`order-summary`、`filter-toolbar`，就不要命名成 `item-wrap`

## 禁止行为

1. 不要为了贴近视觉稿而机械复制多层嵌套框。
2. 不要把几乎所有节点都生成为 `div`。
3. 不要用 `div` / `span` 模拟 `button`、`a`、`label`、`li`、`th` 等语义元素。
4. 不要增加只有一个子节点且无语义、无布局职责的包裹层。
5. 不要先写一堆样式容器，再倒推内容结构。
6. 不要把本应是列表、表单、表格的数据结构退化成纯视觉布局。
7. 不要为了短期“写起来快”牺牲后续可维护性。

## 输出前自检

在输出最终代码前，逐项检查：

1. 是否存在可以替换为语义标签的 `div`
2. 是否存在连续两层及以上纯包裹容器
3. 是否存在错误的交互元素选择
4. 是否存在本应使用 `ul/li`、`form/label`、`table` 却没有使用的区域
5. 是否存在可以抽成子组件的重复结构
6. 是否能从 DOM 结构本身读出页面/组件职责
7. 是否便于后续样式维护、测试选择器编写和局部替换

## 默认输出要求

- 默认输出结构清晰、层级扁平、语义明确的 HTML / JSX / Vue template
- 必要时先用 1 到 3 句概括结构分区，再给代码
- 如果设计稿结构与语义化实现冲突，优先保持语义正确，再通过 CSS 解决视觉问题
- 当用户只要求“实现页面”时，也不要省略结构设计过程

## 一句话准则

前端代码生成时，优先构建“语义正确、层次清晰、职责明确、便于维护”的 DOM；视觉还原不能成为滥用 `div`、制造深层嵌套和牺牲可读性的理由。
